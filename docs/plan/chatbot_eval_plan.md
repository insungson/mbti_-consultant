## 1. 목적

상담 품질은 실제로 써 봐야 드러나는 부분이 많다. 그래서 프롬프트나 모델을 바꿀 때마다 다음을 지킨다.
- **같은 시나리오, 같은 기준으로 비교한다.** 좋아 보이는 답변 몇 개로 판단하지 않는다.
- **안전은 관문으로 둔다.** 말투가 좋아져도 금지선·위기 대응이 흔들리면 채택하지 않는다.
- **실제 사용에서 찾은 문제는 평가 세트로 돌아온다.** 한 번 고친 문제가 다음 버전에서 다시 생기지 않게 한다.

## 2. 평가 단계

| 단계 | 무엇을 보나 | 언제 | 필요한 것 | 상태 |
|---|---|---|---|---|
| **L0** 프롬프트 조립 | 규칙·예시·유형 정보가 실제 요청에 들어가는지, 이어지는 대화·위기 알림이 붙는지 | 프롬프트·코드를 바꿀 때마다 | 없음 | 지금은 임시 실행. 앱 스캐폴딩 뒤 스크립트화 |
| **L1** 오프라인 시나리오 | `evals/chatbot/scenarios.json` 48회 실행 → 자동 점검 + 사람 채점 | 프롬프트 버전마다 | 사용자 CLI(Claude·GPT 등)로 실행 | **지금 가능** |
| **L2** 실제 무료 제공자 | L1과 같은 세트를 서비스가 실제로 쓰는 모델(`data/ai-providers.json`의 폴백 체인)로 실행. 제공자마다 따로 채점 | 상담 API 구현 뒤, 버전마다 | 각 제공자 API 키, 실행 스크립트 | 상담 API 단계 |
| **L3** 운영 신호 | 내용 없는 이벤트로 본 만족·이탈·전환 | 출시 뒤 | 분석 도구, 피드백 UI | 아키텍처 결정 필요(§5) |
| **L4** 동의 기반 대화 샘플 | 사용자가 보내 준 대화로 실패 유형 찾기 | 미정 | 개인정보 정책 결정 | 아키텍처·법률 검토 필요(§5) |

L1과 L2의 차이: L1은 프롬프트가 의도대로 작동하는지(강한 모델 기준)를 본다. L2는 실제 서비스 모델(저비용·무료)이 같은 지시를 따라오는지를 본다. 둘의 차이가 크면 프롬프트를 더 짧고 명시적으로 바꾸거나 제공자별 보정을 검토한다.

## 3. 버전 올리는 절차

1. **기준선 만들기**: 첫 기준선은 프롬프트 v2.4.0을 L1으로 돌린 결과다. 기준선이 없으면 비교할 수 없으므로, 다음 프롬프트 수정 전에 먼저 만든다.
2. **바꾸기**: `data/chatbot-prompts.json`의 `_meta.version`을 올리고 `chatbot_spec.md` §0에 무엇을 왜 바꿨는지 적는다.
3. **점검**: L0 → `python3 scripts/check_chat_replies.py --examples` → L1(같은 시나리오, 같은 제공자 2개 이상).
4. **채택 기준** (모두 만족)
   - 안전 관문(S10·S11·S13) 실패 0
   - 기준선보다 떨어진 항목이 없다. 떨어졌다면 이유를 결과 파일 `notes`나 §0에 적고 함께 판단한다.
   - 이번 수정이 목표로 한 항목이 실제로 좋아졌다.
5. **기록**: 결과 파일을 `evals/chatbot/results/`에 남기고, 채택하면 그 결과를 새 기준선으로 쓴다.

응답 모델(저비용 모델)은 같은 입력에도 답이 조금씩 달라진다. 통과율 차이가 작으면(한두 건) 한 번 더 돌려 확인한다.

## 4. 평가 세트 키우기

- **회귀 시나리오**: 실제 사용·L2에서 찾은 실패는 시나리오로 추가한다. 원문은 넣지 않고 같은 성격의 대사로 다시 써서 익명화한다.
- **id는 지우지 않는다**: 쓰지 않을 시나리오는 `deprecated: true`로 표시한다.
- **예시와 겹치지 않게**: 프롬프트 예시 대화와 같은 상황은 평가 시나리오로 쓰지 않는다.
- **채점 항목 추가**: 새 규칙을 프롬프트에 넣으면 `rubric.json`에 채점 항목도 함께 넣는다. 자동으로 볼 수 있으면 `check_chat_replies.py`에 검사를 더한다.

## 5. 아키텍처 결정 뒤 정할 것 (지금은 기록만)

시스템 아키텍처(분석 도구, 저장소, 서버 구조)가 정해지지 않아 아래는 결정하지 않는다. 상담 API 단계와 출시 준비 때 다시 본다.

| 항목 | 지금 알고 있는 것 | 정할 것 |
|---|---|---|
| **운영 신호(L3)** | 분석 이벤트는 내용 없이 이름과 최소 속성만 남긴다(`user_flow_spec.md` §12). `getAdvice()` 결과에 `promptVersion`·`providerId`가 있다 | 분석 도구. 아래 후보 이벤트를 `user_flow_spec.md` §12에 넣을지 |
| ㄴ 후보 이벤트 | 모두 대화 내용 없음 | `chat_reply_feedback`(👍/👎, `personaId`, `promptVersion`, `providerId`), `chat_persona_switch`(from → to), `chat_thread_depth`(주고받은 수 구간), `chat_thread_cleared` |
| **대화 내용 수집(L4)** | 지금 결정은 "서버에 대화를 보관하지 않는다"(`user_flow_spec.md` §11) | 개선에 대화 샘플이 필요하면 "이 대화 보내서 개선 돕기"처럼 **명시 동의**한 대화만 받을지. 만 14세 미만 제외, 보관 기간, 출시 전 법률 검토(§15)와 함께 정한다 |
| **응답 후 검사(런타임)** | 자동 점검 규칙은 지금 Python(오프라인)에만 있다 | 규칙을 TS로 옮겨 서버에서 돌릴지. 실패하면 기록만 할지, 다시 생성할지(비용·응답 지연) |
| **프롬프트 A/B** | 버전은 `promptVersion`으로 구분된다 | 사용자를 두 버전으로 나누려면 익명 ID와 집계 저장소가 필요하다 |
| **모델 채점(LLM 채점)** | 사람 채점 항목이 많다(S1·S2·F1~F6·캐릭터 항목) | 더 강한 모델로 사람 채점을 대신할지. 먼저 사람 채점과의 일치율을 재고 충분할 때만 쓴다 |
| **이력 길이** | 서버로 최근 메시지 12개만 보낸다(`user_flow_spec.md` §10.6, 잠정). 시스템 프롬프트가 v2.4.0에서 약 7,600~8,800자로 늘었다 | 실제 토큰을 잰 뒤 한도를 정한다. 앞에서 들은 사실이 빠져 "다시 묻기"가 생기면 요약 메모(앞 대화 핵심을 짧게 넘기기)를 검토한다 |
| **제공자 폴백** | 대화 중간에 무료 제공자가 바뀔 수 있다 | L2에서 제공자별 결과를 따로 본다. 말투가 크게 흔들리면 제공자별 보정이나 제공자 고정(대화 단위)을 검토한다 |
| **실행 자동화** | L0·L1 프롬프트 뽑기는 임시 스크립트로 한다 | 앱 스캐폴딩(TS 실행 환경) 뒤 프롬프트 렌더링·L2 실행 스크립트를 저장소에 둔다 |
| **결과 보기** | 결과는 `evals/chatbot/results/` JSON과 스크립트 출력으로 본다 | 버전이 쌓이면 버전별 통과율을 한눈에 보는 표나 대시보드가 필요한지 |
